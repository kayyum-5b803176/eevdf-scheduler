Let me check for real prior art rather than speculate — this is a factual question about existing practice.## Real prior art — yes, this is a known, named problem

What we've built is a real convergence of several documented approaches, not a novel idea:

**Atomic Design** (Brad Frost, 2013) is the closest conceptual match to the template catalog itself — atoms → molecules → organisms → templates → pages, with the explicit rule that dependencies only flow downward: atoms import nothing, molecules import only atoms, organisms import molecules. Your "wardrobe" and "Lego sequence" framing maps directly onto this — `NavCard`/`ToggleCard` are organisms, the pieces inside them are molecules.

**"Slots in Design Systems" by Nathan Curtis** is almost exactly the mechanism we hand-built with `App.Row.TextBlock`/`App.Row.Value`/spacers: a Row component with slots for leading visual, trailing actions and the default content between; slots provide the space for an indeterminate quantity of a single, predictable type of children. Native web components have a literal `<slot>` element for this — HTML got there before we did, just in a different platform.

**The 8-point grid** (Material Design, IBM Carbon, Atlassian, Shopify Polaris, GitHub Primer) is the real-world version of our fixed-increment scale rule — the discrete-scale constraint forces deliberate spacing decisions rather than the eyeballed values that produce unpredictable interfaces, and the reasoning is nearly identical to what you gave me: it scales cleanly across common display densities without producing fractional pixel values.

**Enforcement tooling exists as a whole product category** — `@lapidist/design-lint` flags deviations at commit or build time, not six months later during a painful audit, treating tokens as the only legal source of truth, exactly what `check_ui_geometry.sh` does by hand with grep. Visual regression tools (Percy, Applitools, Lastest) go a level further and walk every rendered node, read its computed color, spacing, radius, and typography values, and map each one back to the nearest token, flagging values that don't resolve to a token — that's a real, shipped version of "does this pixel match the scale," done automatically instead of manually.

One piece is unusually close to our actual situation: a closed token layer the LLM picks from solves the fabrication problem — instead of scattered raw values, you create a named variable and use it everywhere; an audit script that catches what the LLM gets wrong scans files and flags every raw value with the correct token to use instead. That's a documented pattern specifically for AI-assisted design systems, and it's what `check_ui_geometry.sh` already is.

## Where the prior art is stronger than what we've built — my proposal

**1. Move enforcement from "values" to "shape."** Every tool above, including ours, checks *literals* — is this a raw `16dp`, a legacy color, a bad implicit parent. None of it checks *structure* — is a switch a sibling of a subtitle, is a piece out of order. That's still just a written rule in `TEMPLATE_CATALOG.md`, unenforced by anything. This was the original ask, and it's the biggest gap. A real fix: a script that parses each settings layout's XML into a tree and checks it against the catalog's declared piece sequence per template — not grep, an actual structural walk.

**2. Stop hand-copying XML per screen; make illegal shapes physically impossible to write.** Right now every `NavCard` instance is ~15 lines of duplicated `MaterialCardView` + `LinearLayout` + row boilerplate, and correctness depends on a developer copying it right. The stronger version — used by real design systems — is a custom compound `View` class (`NavCardView`) whose constructor/XML attributes only expose legal parameters (`title`, `subtitle?`, `indicatorType`). A developer literally cannot place a switch next to a subtitle, because the class's internals — not a linter, not a doc — are the only thing that ever builds that row. This converts "the catalog says this is illegal" into "there is no code path that can produce this," which is the actual promise the wardrobe/Lego metaphor was making from the start.

**3. One machine-readable source of truth, not two hand-synced ones.** `TEMPLATE_CATALOG.md` (prose) and `themes.xml`/`check_ui_geometry.sh` (implementation) are three separate places I have to remember to update together. A single schema (JSON/YAML: template name → ordered pieces → F/O/S → legal state parameters) could generate the styles, the enforcement rules, *and* the doc, so they can't silently drift from each other the way the doc and code already have once or twice this session.

**4. Screenshot testing on the Render tab we already built.** Since Render now hosts real demo instances of every template, it's a natural fit for Android's Paparazzi or Espresso screenshot tests — render each demo, diff its pixels against a committed baseline, fail CI if a future token change silently shifts a template's actual rendered output. Right now "the demo looks right" is still a manual check; this would close that loop the same way Percy/Applitools do for web.

Ranked by effort-to-value, #1 and #4 are both buildable without a large refactor; #2 is the correct long-term answer but means touching every screen again.
